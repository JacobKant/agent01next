# Архитектура проекта Agent01Next

## Общие принципы

### 1. Модульность
Проект построен на принципах модульной архитектуры:
- Каждый компонент имеет четко определенную ответственность
- Компоненты слабо связаны между собой
- Используется dependency injection для тестируемости

### 2. Разделение ответственности

#### Frontend (src/app/)
- UI компоненты и страницы
- Клиентская логика взаимодействия с пользователем
- Управление состоянием чата

#### Backend API (src/app/api/)
- REST API endpoints
- Обработка HTTP запросов
- Валидация входных данных

#### Бизнес-логика (src/lib/)
- Исполнители чата (chat-executor)
- Интеграции с внешними сервисами (openrouter, huggingface)
- Работа с базой данных (db)
- Планировщик задач (scheduler)

#### MCP Серверы (src/mcp/)
- Изолированные серверы для расширения функциональности
- Каждый сервер предоставляет набор инструментов (tools)
- Коммуникация через stdio transport

### 3. Типизация
- Использование TypeScript для всех компонентов
- Строгая типизация данных (Zod для валидации)
- Типы определены в `src/types/`

## Структура компонентов

### MCP Клиент (src/lib/mcp-client.ts)

**Ответственность:**
- Подключение к множественным MCP серверам
- Управление жизненным циклом соединений
- Конвертация MCP tools в формат OpenAI
- Маршрутизация вызовов инструментов к нужным серверам

**Принципы:**
- Singleton паттерн для управления соединениями
- Автоматическое переподключение при ошибках
- Изоляция ошибок между серверами

### Chat Executor (src/lib/chat-executor.ts)

**Ответственность:**
- Выполнение диалога с LLM
- Обработка tool calls в цикле
- Управление промежуточными сообщениями
- Агрегация использования токенов

**Принципы:**
- Итеративный подход к выполнению tool calls
- Защита от бесконечных циклов (maxIterations)
- Сохранение всех промежуточных сообщений

### База данных (src/lib/db.ts)

**Ответственность:**
- Инициализация SQLite базы данных
- CRUD операции для чатов и сообщений
- Миграции схемы БД

**Принципы:**
- Использование WAL режима для производительности
- JSON хранение для гибкости схемы
- Индексы для быстрого поиска

### Планировщик (src/lib/scheduler.ts)

**Ответственность:**
- Регистрация задач
- Запуск задач по расписанию (cron)
- Управление жизненным циклом задач

**Принципы:**
- Декларативное определение задач
- Изоляция ошибок выполнения задач
- Логирование всех операций

## Паттерны проектирования

### 1. Factory Pattern
- Создание MCP клиентов через конфигурацию
- Создание задач планировщика через регистрацию

### 2. Strategy Pattern
- Разные провайдеры LLM (OpenRouter, HuggingFace)
- Разные типы MCP серверов (локальные, npm пакеты)

### 3. Observer Pattern
- Обновление UI при изменении состояния чата
- Логирование событий выполнения задач

### 4. Adapter Pattern
- Конвертация MCP tools в формат OpenAI
- Адаптация различных форматов ответов LLM

## Правила разработки

### 1. Добавление нового MCP сервера

1. Создать файл сервера в `src/mcp/`
2. Реализовать сервер используя `@modelcontextprotocol/sdk`
3. Зарегистрировать в `src/lib/mcp-client.ts` в массиве `servers`
4. Добавить документацию в `doc/MCP_SERVERS.md`

**Пример:**
```typescript
{
  name: "my-new-server",
  serverPath: join(process.cwd(), "src", "mcp", "my-server.ts"),
}
```

### 2. Добавление новой задачи планировщика

1. Создать файл задачи в `src/lib/tasks/`
2. Экспортировать объект типа `ScheduledTask`
3. Импортировать и зарегистрировать в `src/lib/scheduler-init.ts`
4. Добавить документацию в `doc/SCHEDULER.md`

**Пример:**
```typescript
export const myTask: ScheduledTask = {
  id: "my-task",
  name: "Моя задача",
  cronExpression: "0 9 * * *", // Каждый день в 9:00
  enabled: true,
  execute: async () => {
    // Логика задачи
  },
};
```

### 3. Работа с базой данных

- Все операции с БД должны быть в `src/lib/db.ts`
- Использовать prepared statements для безопасности
- Обрабатывать ошибки и логировать их
- Не создавать прямые соединения с БД в других модулях

### 4. Обработка ошибок

- Использовать try-catch для асинхронных операций
- Логировать ошибки с контекстом
- Не прерывать выполнение при ошибках в изолированных компонентах (например, MCP серверы)
- Возвращать понятные сообщения об ошибках пользователю

### 5. Логирование

- Использовать префиксы для идентификации компонента: `[Component Name]`
- Логировать важные события (подключения, вызовы инструментов, ошибки)
- Не логировать чувствительные данные (токены, пароли)

## Безопасность

### 1. Переменные окружения
- Никогда не коммитить `.env.local` в репозиторий
- Использовать `.env.local.example` как шаблон
- Валидировать наличие обязательных переменных при старте

### 2. SQL Injection
- Использовать prepared statements для всех SQL запросов
- Не использовать конкатенацию строк для SQL

### 3. API Security
- Валидировать все входные данные
- Ограничивать размер запросов
- Использовать rate limiting для публичных endpoints

### 4. MCP Серверы
- Изолировать выполнение серверов
- Валидировать входные параметры инструментов
- Ограничивать доступ к файловой системе

## Производительность

### 1. База данных
- Использовать индексы для часто запрашиваемых полей
- Использовать WAL режим для лучшей производительности
- Ограничивать размер запросов истории чата

### 2. MCP Клиент
- Переиспользовать соединения между запросами
- Закрывать соединения после использования
- Ограничивать время выполнения инструментов

### 3. LLM Запросы
- Кэшировать результаты где возможно
- Использовать суммаризацию для длинных диалогов
- Ограничивать максимальное количество токенов

## Масштабируемость

### Горизонтальное масштабирование
- База данных может быть вынесена в отдельный сервис
- MCP серверы могут быть запущены как отдельные процессы
- Использовать Redis для кэширования и очередей

### Вертикальное масштабирование
- Оптимизировать запросы к БД
- Использовать connection pooling
- Кэшировать результаты эмбеддингов
